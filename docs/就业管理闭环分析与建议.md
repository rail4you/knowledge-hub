# 就业管理闭环：现状问题与推荐方案

> 本文是「就业管理工作台」上线时对现有 岗位发布 / 投递 / 面试 / 就业去向 / 就业统计 五个环节的梳理结论。
> 工作台入口：`/admin/employment/workbench`（菜单「就业管理工作台」）。
> 统计口径：**只统计当前租户内的学生**（拥有 `Student` 角色且 `TenantId != null`），不统计社会学校 / 外部学员。

## 一、现在的闭环长什么样

```
① 岗位发布            ② 岗位投递              ③ 面试                  ④ 就业去向            ⑤ 就业统计
JobPosting    ──→   JobApplication   ──→   InterviewSchedule  ──→  EmploymentOutcome  ──→  统计/导出
Draft/Pending/      Submitted/Viewed/      Pending/Passed/         Intention/Signed/
Published/Closed    InterviewScheduled/    Deferred/Failed         Employed/FurtherStudy/
                    InterviewCompleted/                            Entrepreneurship/Unemployed
                    Offered/Rejected                               + IsVerified 核实
```

| 环节 | 数据表 | 状态机 | 谁能操作 |
|---|---|---|---|
| 岗位发布 | `AppJobPostings` | 草稿 → 待审 → 已发布 / 已驳回 → 已关闭 | `Employment.PublishJob`（企业 / 学校）、`ReviewJob`（学校审核） |
| 岗位投递 | `AppJobApplications` | 已投递 → 已查看 → 面试中 → 面试完成 / 已录取 / 已拒绝 / 已撤回 | 学生投递；`ManageApplication` / `ScheduleInterview` 推进 |
| 面试 | `AppInterviewSchedules` | 待面试（Pending）→ 通过 / 待定 / 未通过；可再标记「面试完成」 | `Employment.ScheduleInterview` |
| 就业去向 | `AppEmploymentOutcomes` | 意向 / 已签约 / 已就业 / 升学 / 创业 / 待就业 + `IsVerified` 学校核实 + `IsPrimary` 主要去向 | `Employment.ManageOutcome` |
| 就业统计 | 无独立表 | 由投递 + 去向汇总 | `Employment.ViewStatistics` |

## 二、发现的问题（按严重程度排序）

### P0 — 面试结果不会自动进入就业去向（闭环断了）

`RecordInterviewResultAsync` 里「面试通过」只把投递状态改成 `Offered`，**没有生成 `EmploymentOutcome`**。
所以「面试通过 → 就业去向」这一段完全靠老师手工再录一遍，而且两边没有关联（`EmploymentOutcome.ApplicationId` 允许为空）。

后果：岗位和去向是两套数据，就业率算不到面试通过的人；老师容易漏录。
库里现状也印证了这一点：投递 3 条、面试 1 场、去向 2 条，三者对不上。

### P0 — 就业统计的数据源是「投递」，不是「去向」

`GetStatisticsAsync` 统计的是 `JobApplication`，并且有两处明显错误：

```csharp
Status = (EmploymentOutcomeStatus)(int)x.Status,   // 把投递状态硬转成去向状态
IsVerified = x.ResumeSnapshotJson != null,         // 有简历快照就算"已核实"
```

投递状态（0~6）和去向状态（0~5）枚举含义完全不同，转换后全是错的；「有没有简历快照」也和「学校是否核实去向」无关。

现状：统计页实际用的是 `getApplicationStats` + `getOutcomeList` 两个接口拼出来的图，`GetStatisticsAsync` / 导出 `ExportStatisticsAsync` 仍走错误口径。

### P1 — 「多个就业去向 + 一个主要去向」缺少强约束

- 业务上允许多条去向是**合理的**：专升本 + 签约、签约后再换工作、同时有实习和正式 offer，都需要留痕。
- 但「主要去向」只在 `SaveOutcomeAsync` / 导入时**用代码临时取消别人的 IsPrimary**，数据库没有约束。
  实测库里同一个学生已经有 **2 条 IsPrimary = true**（并发保存 / 导入与手工混用时会破）。

### P1 — 核实是「逐条」的，没有「一个学生一次核实」的概念

现在 `VerifyOutcomeAsync(id, verified)` 只改一条记录。于是出现三个问题：
1. 一个学生有 3 条去向，老师要核实 3 次，很啰嗦；
2. 核实了 A 条，B 条还是「待核实」，统计里同一学生既算「已核实」又算「待核实」，数字看着矛盾；
3. 到底哪条算「这个学生的就业结果」没有唯一答案 —— 就业率按哪条算？现在按「任一已核实且已落实」算，没人说得清。

### P1 — 就业率没有统一口径

- 工作台：已核实且状态 ∈ {签约, 就业, 升学, 创业} 的学生数 ÷ 租户学生总数；
- 统计页：按投递的 `EmploymentOutcomeStatus`（错误来源）分组；
- 导出：另一套按投递统计。

三处口径不一致，同一个学校会看到三个不同的就业率。

### P2 — 学生范围没有统一过滤

多处查询用 `DataFilter.Disable<IMultiTenant>()` 后按 `TenantId` 过滤，但学生集合有的取「有简历的人」、有的取「投递过的人」、有的取「有去向的人」。
社会学校 / 外部学员（不属于任何租户的用户）在部分聚合里会被算进来。工作台已改为「拥有 `Student` 角色且 `TenantId != null`」，其它页面还没统一。

### P2 — 岗位 → 投递 → 面试缺少「企业侧」的可见性约束

`GetJobApplicationListAsync` 上叠了三个 `[Authorize]`（`PublishJob` / `ManageApplication` / `ScheduleInterview`），
ABP 的 `[Authorize]` 是「全部满足」还是「任一满足」取决于实现，目前写法容易让企业用户看到别家企业的投递
（企业只有 `PublishJob`）。建议改成显式的「本企业岗位 OR 学校管理员」判断。

## 三、推荐方案

### 方案 A（推荐）：把「学生就业结果」独立成一个被核实的终态

保留多条去向（留痕），但明确「**一个学生只有一个已核实的终态去向**」：

1. **数据层**
   - `EmploymentOutcome` 加 `StudentOutcomeState`：`Pending / Verified / Superseded`（或复用 `IsVerified` + `SupersededBy`）。
   - 加 Postgres 部分唯一索引，硬保证一个学生最多一条主要去向、最多一条已核实终态去向：
     ```sql
     CREATE UNIQUE INDEX ux_outcome_primary
       ON "AppEmploymentOutcomes" ("TenantId", "StudentId") WHERE "IsPrimary" AND NOT "IsDeleted";
     CREATE UNIQUE INDEX ux_outcome_verified
       ON "AppEmploymentOutcomes" ("TenantId", "StudentId") WHERE "IsVerified" AND NOT "IsDeleted";
     ```
     （先跑一次性修数据脚本：每个学生只保留 `ConfirmedAt` 最新的一条 IsPrimary。）
2. **核实语义**
   - `VerifyOutcomeAsync(id, verified=true)` 时，把该学生**其它**去向自动标记为 `Superseded`（不需要再逐条核实）；
   - 取消核实时，原来的其它去向可选恢复为 `Pending`（提示老师确认）。
   - 即：**核实一条 = 确认这个学生的就业结果，其它去向不再需要核实**。
3. **就业率口径**统一为：`已核实终态且状态 ∈ {签约, 就业, 升学, 创业}` 的学生数 ÷ 租户学生数。
   三处（工作台 / 统计 / 导出）共用同一个服务方法，避免再各算一套。

### 方案 B：面试通过自动生成「待核实去向」

`RecordInterviewResultAsync(Passed)` 时：
- 若该学生还没有「已核实终态去向」，自动创建 `EmploymentOutcome`（`Status = Intention` 或 `Signed`，
  `ApplicationId = 投递 id`，`IsPrimary = 该学生还没有主要去向`，`IsVerified = false`），
  并给老师一条待办「面试通过，请补全并核实就业去向」；
- 若已有已核实终态去向，则只做提示，不覆盖。

这样「面试 → 去向」自动接上，`EmploymentOutcome.ApplicationId` 也真正起作用（可以从去向反查岗位/面试）。

### 方案 C：统计接口重写

- `GetStatisticsAsync` 改为以 `EmploymentOutcome` 为数据源（只算已核实的终态），按 专业 / 年级 / 状态 分组；
- `ExportStatisticsAsync` 复用同一份数据；
- 保留 `GetApplicationStatsAsync` 作为「投递活跃度」看板，两个指标明确分开命名：
  **就业率（去向口径）** vs **投递活跃度（投递口径）**。

### 方案 D：学生范围统一

抽一个 `IEmploymentStudentScope`（或私有方法）：
`拥有 Student 角色 && TenantId == 当前租户`，所有就业统计 / 下拉 / 导出都复用它。
工作台已经按这个口径实现，可作为参考实现。

### 方案 E：权限收敛

`GetJobApplicationListAsync` 改成：
- 学校侧（`ManageApplication` 或 `ScheduleInterview`）→ 本租户全部投递；
- 企业侧（只有 `PublishJob`）→ 仅 `JobPosting.EnterpriseProfileId / EmployerUserId` 属于本企业的投递。
