# 域名绑定多租户 · 技术方案（待评估）

> 目标：每所学校有自己的域名（或子域名）；通过该域名访问时，系统只显示**本租户**的资源库内容，
> 登录账号也必须是**本租户**的账号。
>
> 本文只做方案设计，不含代码改动。评估通过后再进入开发。

---

## 〇、结论先行

**ABP 后端与前端都原生支持域名多租户**，但直接套用 ABP 默认实现有两处与需求相悖，所以本方案是
「**用 ABP 的扩展点，但自己实现解析器**」：

| ABP 原生能力 | 位置 | 能否直接用 |
|---|---|---|
| 后端域名租户解析 | `DomainTenantResolveContributor` + `AbpTenantResolveOptions.AddDomainTenantResolver(domainFormat)` | ⚠️ 只认「子域名 == 租户 Name」，不支持每校独立域名；且解析顺序令牌优先 |
| 前端子域名解析 | `environment.application.baseUrl` 写 `https://{0}.example.com`，ABP Angular 自动 `findTenantByName` 并隐藏租户框 | ❌ 同样按租户名查；平台域名下 `{0}` 为空会把 baseUrl 拼成 `https://.example.com` |

两处「相悖」的具体含义：

1. **不支持自定义域名**。需求原文是「每个租户学校，都有自己的域名**或者**子域名」——
   `www.qidi-edu.cn` → qidi 租户这种映射，ABP 的 `DomainFormat` 模板表达不了
   （它只做「固定后缀 + 前缀即租户名」的字符串提取）。
2. **令牌优先于域名**。ABP 的解析链是
   `CurrentUser(令牌) → QueryString → Route → Header → Cookie`，
   `AddDomainTenantResolver` 把域名解析器插在 `CurrentUser` **之后**。
   结果是：持有 qidi 令牌的教师访问 `guozhou.example.com`，仍会看到 qidi 的内容——
   与「账户也是自己租户的」矛盾。

本方案用一个**自研 `ITenantResolveContributor` 插到解析链最前面**来同时解决这两点。

## 一、域名 → 租户 的数据映射

### 1.1 存哪里

落在上一轮刚建的 `School` 实体上（它与租户 1:1，是「机构档案」，域名是机构的自然属性）：

| 字段 | 类型 | 说明 | 索引 |
|---|---|---|---|
| `Domain` | `string?` | **完整域名**，支持每校独立域名，如 `qidi-edu.cn` | 唯一（可空） |
| `Slug` | `string?` | **子域名前缀**，如 `qidi`（用于 `*.example.com`） | 唯一（可空） |

平台基础域名用全局设置承载：`KnowledgeHub.Domain.BaseDomain`（如 `example.com`），
与 `KnowledgeHub.PublicSchool.TenantId` 同级，由 host 超管在管理端维护。

> 备选：存 ABP `Tenant.Properties` 扩展属性字典。好处是不改表；坏处是无法建唯一索引、
> 查询要全表扫且易被误改。**推荐用 `School` 的独立字段。**

### 1.2 解析算法

```
输入：HTTP Host 头
 1. 取 HostString.Host        ← 只要主机名，去掉端口（本地开发 qidi.localhost:4200 才能用）
 2. 去协议前缀、转小写
 3. 精确匹配 School.Domain == host                    → 命中租户
 4. host 以 "." + BaseDomain 结尾 → 取前缀 slug
      匹配 School.Slug == slug                        → 命中租户
 5. 都不中 → 本解析器不处理（交回 ABP 默认链）
```

第 4 步的「BaseDomain 结尾」判断要**排除平台域名本身**：
`example.com` 与 `www.example.com` 都不是学校域名，必须能匹配到 host 上下文，
否则平台级管理端会被误判成租户。

### 1.3 性能

解析发生在**每个请求**上，不能每次查库。方案：
- `IDistributedCache<string, Guid?>` 缓存 `host → tenantId`，TTL 5 分钟
- `School` 的 `Domain`/`Slug` 变更时主动失效对应 key
- 查库走唯一索引，单行命中

## 二、租户解析链（关键设计）

自研解析器**插到 `AbpTenantResolveOptions.TenantResolvers` 的 index 0**（在 `CurrentUser` 之前）：

```
0. DomainTenantResolveContributor（自研）   ← 新增
1. CurrentUserTenantResolveContributor      ← ABP 默认（令牌 tenantid 声明）
2. QueryString / Route / Header / Cookie    ← ABP 默认（__tenant 头与 Cookie）
```

### 2.1 由此得到的语义

| 场景 | 域名解析 | 令牌租户 | 实际生效 | 结果 |
|---|---|---|---|---|
| 游客访问 `qidi.example.com` | qidi | — | qidi | ✅ 只看到 qidi 的内容 |
| qidi 教师访问 `qidi.example.com` | qidi | qidi | qidi | ✅ |
| qidi 教师访问 `guozhou.example.com` | guozhou | qidi | **guozhou** | ⚠️ 见下 |
| 访问平台域名 `www.example.com` | 无命中 | — | 走默认链 | ✅ 平台级门户 + host 管理端照旧 |
| host 管理员在平台域名 | 无命中 | host | host | ✅ |

### 2.2 「令牌与域名不一致」怎么处理 —— **需要你拍板**

因为域名解析器在最前，qidi 令牌出现在 guozhou 域名时，请求上下文是 guozhou，
而 OpenIddict 校验令牌时会比对上下文租户与令牌租户 → **令牌失效 → SPA 收到 401**。

这在安全上是对的（账号确实不能跨校用），但体验上会变成「莫名其妙 401」。两个选项：

- **A（推荐）域名优先 + 友好提示**：令牌失效时，登录页检测到「该账号属于 X 学校，当前域名是 Y 学校」，
  明确提示「此账号属于 X 学校，请访问 X 的域名登录，或使用 Y 学校的账号」。
  实现上：登录页在 401 后调一次 `/api/public/current-tenant` 与账号所属租户比对，给出可读文案。
- **B 令牌优先（ABP 默认）**：域名只作为「首次进入的入口」，登录后跟着令牌走。
  实现成本最低，但「域名绑定」的约束感弱，且与「账户也是自己租户的」有出入。

### 2.3 host 管理员在学校域名

host 管理员在 `qidi.example.com` 会被解析成 qidi 租户 → 打开 host 专属页面会 403/401。
**策略建议**：host 管理端只在平台域名使用（`/admin-login` 在学校域名下自动跳平台域名）。
若贵方希望 host 能进学校域名做运维，需要额外开「host impersonation 租户」的通路，工作量另计。

## 三、后端改造清单

### 3.1 领域层

| 项 | 内容 |
|---|---|
| `School` 实体 | 加 `Domain` / `Slug` 字段 + 唯一索引（迁移） |
| `School` 领域方法 | `SetDomain` / `SetSlug`，规范化（转小写、去空白、去端口、去协议前缀） |
| 冲突校验 | `Domain` / `Slug` 唯一；`Domain` 不允许等于平台域名或 BaseDomain |

### 3.2 租户解析

| 项 | 内容 |
|---|---|
| `DomainTenantResolveContributor`（自研） | 实现 `ITenantResolveContributor`，读 Host → 查缓存 → 查库 → 返回 tenantId；命中时 `context.Handled = true` |
| 注册 | 在 `KnowledgeHubDomainModule`（或 HttpApiHostModule）`Configure<AbpTenantResolveOptions>` 里 `options.TenantResolvers.Insert(0, ...)` |
| 缓存 | `IDistributedCache<string, Guid?>` + 变更失效 |

> 注意：ABP 自带的 `DomainTenantResolveContributor` 不需要注册，避免两套并存打架。

### 3.3 公开接口（新增）

`GET /api/public/current-tenant`（匿名）——给前端判断「当前域名是不是某所学校」：

```json
{
  "isSchoolDomain": true,
  "tenantId": "3a20...",
  "tenantName": "qidi",
  "schoolName": "启迪学院",
  "logoUrl": "https://...",
  "baseDomain": "example.com"
}
```

放在已有的 `TenantListController`（路由前缀 `api/public`）里最省事。

同时**收敛** `GET /api/public/tenants`（现在返回全量租户列表给登录页下拉）：
学校域名下应只返回当前学校，或返回空数组让前端隐藏下拉。**这是必须做的**，
否则等于把「有哪些学校、他们叫什么」公开给了任意访客。

### 3.4 门户（首页 / 公开内容页）收窄

`PortalAppService` 现在有 5 处跨租户聚合：

| 方法 | 现状 |
|---|---|
| `GetPublicTenantListAsync` | 聚合所有租户 → 首页资源库卡片列表 |
| `GetPublicHomeStatsAsync` | 聚合全平台课程/资源/微专业数 |
| `GetTopResourcesByDownloadAsync` | 全平台热门资源 |
| `GetPublicBrowseAsync` | 跨租户浏览（课程/资源/微专业） |
| `GetHomeDataAsync` | 跨租户首页数据 |

**方案：方法签名不动，在服务内按 `CurrentTenant.Id` 收窄**——

```csharp
// 有租户上下文（学校域名）→ 只返回本租户
// host 上下文（平台域名）→ 保持现状，聚合所有学校做平台级展示
```

这样「学校域名只显示自己租户的内容」和「平台域名继续做全景展示」两个诉求同时满足，
且不需要为每个接口新增参数。

### 3.5 与既有能力的关系

| 能力 | 是否需要改 |
|---|---|
| 跨校共建资源库（上轮） | ❌ 不用改。`ResourceLibrary` 按 `OwnerTenantId` / `MemberTenantId` 判定，与域名正交 |
| 资源共享 `ResourceShare` | ❌ 不用改。按 `TargetTenantId == CurrentTenant.Id` 判定，域名解析后自然正确 |
| 课程共享 `CourseShare` | ❌ 不用改，同上 |
| 公开注册（社会学校） | ⚠️ 建议把注册入口挂到社会学校自己的域名下（它也是一个租户），`PublicRegistrationAppService` 内部用 `CurrentTenant.Change(socialSchoolTenantId)` 的逻辑**不受影响** |
| 学校简介页 `/school/:id` | ⚠️ 学校域名下应直接进本校简介（去掉"从列表里选"这一步） |

## 四、前端改造清单

### 4.1 核心认知：API 调用几乎不用改

SPA 的所有 API 请求都走**同源** `/api`（Nginx 反代到 API 容器，且已带 `proxy_set_header Host $host`），
所以浏览器发出的 Host 头天然带着学校域名，**后端解析器直接生效**。

前端真正要改的只有 4 处：

### 4.2 改动明细

| # | 位置 | 改动 |
|---|---|---|
| 1 | 启动（`app.config.ts` / `app.component.ts`） | 启动时先调 `/api/public/current-tenant`；若 `isSchoolDomain=true`，**清掉残留 `__tenant` cookie** 并把 `sessionState.tenant` 固定为该租户（否则旧 cookie 会让 SPA 自带租户与域名打架） |
| 2 | 登录页（`login.component.ts`） | 学校域名下隐藏「机构」下拉，固定显示该校校名+校徽；`/admin-login`（host 登录）在此域名下提示「请到平台域名登录」 |
| 3 | 登录失败提示 | 401 时用 `/api/public/current-tenant` 与账号归属租户比对，输出「此账号属于 X 学校，当前站点是 Y 学校」（配合 §2.2 方案 A） |
| 4 | 首页 / 公开内容页 | 学校域名下不再拉全量租户列表（后端已收窄，前端按 `isSchoolDomain` 决定是否渲染"全部资源库"区块） |

### 4.3 不用 ABP 的 `{0}` 占位符

`environment.application.baseUrl` 保持**绝对平台地址**（如 `https://www.example.com`）而不是 `https://{0}.example.com`：

- ABP 的 `{0}` 方案按**租户名**查租户 → 不支持自定义域名
- 平台域名下 `{0}` 解析为空 → baseUrl 被拼成 `https://.example.com` → 整个 SPA 资源加载失败
- 我们的场景是「同域不同路径」+「API 同源反代」，本来就不需要按域名切换 baseUrl

## 五、部署与运维

### 5.1 Nginx（生产）

现状是 `server_name _` 兜底 + 单证书，且**所有反代 location 都已带 `proxy_set_header Host $host`** ——
这部分**零改动**，域名信息已经能传到 API。

需要改的是 **TLS 与 server_name**：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A（推荐）逐域名签发 + reload** | certbot 按需为每个学校域名签发证书，`server_name` 列表用 `map`/include 动态生成，签发后 `nginx -s reload` | 学校会持续增加，证书数量可控 |
| B 单证书多 SAN | 手工维护一张含所有 SAN 的证书 | 学校数量少且稳定，否则续期成本高 |

要点：
- 学校域名证书到期必须能告警（否则整个学校站点突然不可用）
- 保留默认 `server_name _` 兜底（平台域名 + 未签发域名的提示页）
- HSTS / 安全响应头按域名差异化时，注意不要在子域名上误伤跨子域的 OSS 静态资源

### 5.2 本地开发

| 项 | 做法 |
|---|---|
| hosts | `/etc/hosts` 加 `127.0.0.1 qidi.localhost guozhou.localhost` |
| Angular dev server 代理 | `proxy.conf.js` 的 `/api` 目前是 `changeOrigin: true` → **会把 Host 改写成 `localhost:44305`，域名信息丢失**。需改为 `changeOrigin: false`（或只对需要域名的路径关闭） |
| 端口 | 自研解析器取 `HostString.Host`（不含端口），所以 `qidi.localhost:4200` 也能正确解析 |
| BaseDomain | 本地把 `KnowledgeHub.Domain.BaseDomain` 设为 `localhost` |

### 5.3 域名管理入口

管理端新增「学校 → 域名」配置（挂在上一轮的 `/admin/school` 页）：
- 学校管理员只能改**自己学校**的域名
- host 超管可查看/代改全部
- 域名冲突实时校验（唯一索引 + 友好错误）
- 建议：域名变更后**保留旧域名一段时间**做跳转（避免已发出去的链接 404）

## 六、实施分期与工作量估算

| 阶段 | 内容 | 产出 | 规模 |
|---|---|---|---|
| **P0 后端底座** | `School` 加 `Domain`/`Slug` + 迁移；自研解析器 + 缓存；`/api/public/current-tenant`；`/api/public/tenants` 收敛 | 后端可按域名正确落租户 | 中（约 8~10 个文件） |
| **P1 门户收窄** | `PortalAppService` 5 处按 `CurrentTenant.Id` 收窄 | 学校域名只显示自己内容 | 小（约 1 个文件，但需逐处确认口径） |
| **P2 前端** | 启动租户种子、登录页锁定、401 友好提示、首页区块裁剪 | 前端与域名一致 | 中（约 5~6 个文件） |
| **P3 部署** | Nginx 多域名 + 证书签发与 reload；hosts 本地调试；dev proxy 改 `changeOrigin` | 可访问 | 小~中（配置为主） |
| **P4 管理端** | 学校域名配置页、冲突校验、旧域名跳转 | 可运营 | 小 |

**建议先做 P0 + P1**，这两步做完就能用 curl 验证「域名 → 租户 → 内容收窄」的主链路，
风险最低；P2 之后再补前端体验。

## 七、风险与边界

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 令牌与域名不一致 | 跨校访问变成 401，体感像"系统坏了" | §2.2 方案 A 的友好提示；错误日志区分"令牌租户不匹配"与"真未登录" |
| 2 | 子域名证书运维 | 学校数增长 → 证书签发/续期成本 | P3 用 certbot 按需签发 + 到期告警；域名列表配置化 |
| 3 | 平台域名被误判为租户 | host 管理端进不去 | 解析器显式排除平台域名与 BaseDomain 本身；加单测覆盖 |
| 4 | `__tenant` cookie 残留 | 旧 cookie 让 SPA 自带租户与域名打架 | 启动时按 `isSchoolDomain` 强制清 cookie + 固定 sessionState |
| 5 | `/api/public/tenants` 泄露租户清单 | 任意访客可枚举所有学校 | P0 一并收敛为「只返回当前域名命中的学校」 |
| 6 | 反代丢 Host | 域名解析失效（回落到 header/cookie，行为退化成今天） | 已确认生产 Nginx 全部 location 带 `Host $host`；dev proxy 需改 `changeOrigin` |
| 7 | 域名指向错误租户 | 学校资源错挂 | 域名唯一索引 + 变更审计日志 + 管理端二次确认 |
| 8 | 未配域名的租户 | 该校仍走旧的租户下拉选学校 | 兼容期：域名未配置时维持现状（老逻辑不破），配置后自动切换 |

## 八、与上一轮多校资源库需求的关系

两条需求**正交**，不冲突：

- 域名绑定决定「**你是谁**（哪个租户的上下文）」
- 多校共建 / 资源共享决定「**你能看到谁的内容**」

组合后的行为示例：

| 访问位置 | 上下文 | 可见内容 |
|---|---|---|
| `qidi.example.com`（qidi 校） | qidi | qidi 自己的资源库 + 共建库 + 共享给 qidi 的 |
| `guozhou.example.com`（guozhou 校） | guozhou | guozhou 自己的 + 共建库 + 共享给 guozhou 的 |
| `www.example.com`（平台） | host | 全平台学校聚合（现状） |

上一轮落在 `School` 实体上的字段（校名/徽标/简介）与本轮的 `Domain`/`Slug` 是同一张表，
可以合并为一次迁移。
